# Lattice v0.7 — AMA architecture support

Document status: design proposal, ready for review
Driver: the v0.6 release closed the visibility + verification gaps
on existing codebases. v0.7 adds opt-in support for the AI-Agentic
Modular Architecture (AMA) — the proposed *forward* shape for
greenfield projects that want sub-5000-token feature isolation
enforced at lint time, not just described in YAML.

AMA and Lattice are the same problem from opposite sides: AMA
constrains *how code is written*; Lattice describes *what code
means*. v0.7 lets the two compose without forcing either side on
brownfield projects.

---

## 1. Premise

After v0.6 a Lattice operator can ask "is what we built what we
asked for?" and get an answer. They cannot ask "is the codebase
shaped so an AI agent can act on one feature without loading a
hundred files?" — the AMA invariants (vertical slicing, no
cross-feature imports, file/method line caps, CQRS) aren't
modeled.

v0.7 adds the missing enforcement layer, but only on opt-in.
Existing brownfield projects (including DevelopersPortal) keep
working unchanged. Greenfield projects that choose
`--architecture ama` at init time get the full enforcement stack.

The intersection is favorable: when AMA is on, the v0.6 RTM
naturally becomes more useful — every business goal traces to a
small isolated block, and "shrink the criterion to one slice"
is a refactor an agent can perform without coordination.

---

## 2. Three streams

### α. Built-in AMA structural checks

Five new structural checks shipped in `pkg/lattice/validate` and
runnable individually via `lattice structural-checks run`:

| Code | Severity | Trigger |
|---|---|---|
| `CROSS_FEATURE_IMPORT` | error (`ama_mode`) / warning (off) | Feature A's symbol imports anything in Feature B's namespace that isn't a published contract (`Core/Contracts/*`). |
| `FEATURE_NOT_COLOCATED` | warning | A feature's symbols span more than one top-level directory. |
| `FILE_LINE_CAP` | warning | A source file exceeds the configured line cap (default 150). Per-file-class override (e.g. DTO 250). |
| `METHOD_LINE_CAP` | warning | A method/function exceeds the configured line cap (default 25). |
| `MIXED_COMMAND_QUERY` | warning | One capability's symbols both write state (mutate db / publish event) and return read data. |

Schema additions (both backward-compatible):
- `Manifest.Capabilities[].Kind: command | query | mixed` —
  defaults to `mixed` so existing manifests don't trip.
- Optional `config.architecture.ama_mode: true` to flip
  `CROSS_FEATURE_IMPORT` to error and tighten other thresholds.

The first three checks are detectable from the existing call
graph + IR; the last two need light per-symbol AST inspection,
which the adapter layer already does.

### β. `lattice feature spec <id>` — `.ai-spec.md` emitter

`lattice feature spec checkout.refund [--out .ai-spec.md]`
produces the AMA-shaped feature summary:

```markdown
# checkout.refund

> Customer-initiated refunds for orders in the return window.

## Inputs
- POST /api/refunds → CreateRefundRequest { order_id, reason? }
- (CLI) lattice-internal refund retry --order <id>

## Outputs
- 200 RefundResponse { refund_id, status, amount }
- 4xx RefundError { code, message } — see "Errors" below

## System Side Effects
- mutates: refunds (insert), orders (status = refunded)
- emits: refund.completed.v1 → payments.gateway
- reads: order, customer

## Invariants
- INV-1: refund.amount ≤ order.charged_amount
- INV-2: refund.status ∈ {pending, completed, failed}

## Errors
- REFUND_OUTSIDE_WINDOW (409)
- REFUND_ALREADY_ISSUED (409)
- REFUND_GATEWAY_DOWN (503)
```

Fully derived from the manifest — `purpose`, `surface[]`,
`errors[]`, `invariants[]`, `capabilities[].rules`. ≤500 words by
design (the cap is enforced; if a feature's spec would exceed it,
the renderer emits a `FEATURE_SPEC_TOO_LARGE` info violation
suggesting decomposition).

Optional LLM polish via the v0.2.1 tone contract, but the
deterministic fallback always works.

### γ. `--architecture ama` scaffold template

```sh
lattice init --scope greenfield --architecture ama
```

Writes:
- `src/Core/Contracts/` and `src/Features/` skeleton with READMEs
- `lattice/config.yaml` with `architecture: ama` and the 5
  structural checks pre-registered
- `lattice/architecture/ama.md` capturing the rules a human
  contributor needs to know (1 page, links back to this proposal)
- Onboarding wizard step 4 surfaces the choice when scope is
  `greenfield` and the project has no existing source tree.

Brownfield projects are explicitly never auto-converted. A
documented `lattice migrate --to ama` is left as a v0.8+
exploration.

## 3. Out of scope (for v0.7)

- **Forcing AMA on brownfield** — the structural checks default
  to warning when `ama_mode: false`. Existing Laravel /
  Django / Rails / Express codebases can adopt the checks
  one at a time.
- **Migration tooling** (Strangler Fig partial conversion).
  Documented pattern only; no automated extractor.
- **Multi-language AMA** — first cut is TypeScript / Python /
  PHP (the adapters we already have). Go, Rust, Java land later.
- **Network-mediated AMA** — AMA itself is monolith-first; a
  microservice variant is a separate proposal.
- **Test-result ingestion** still v0.7+ territory (called out
  in v0.6 too) — without it the AMA `Component.test.ts` check
  only verifies "exists," not "passes."

## 4. Phasing

| Phase | Scope | Commit prefix |
|---|---|---|
| α | Capability.Kind + 5 structural checks + ama_mode config | `v0.7.0-α` |
| β | `lattice feature spec` + `.ai-spec.md` template + FEATURE_SPEC_TOO_LARGE rule | `v0.7.0-β` |
| γ | `--architecture ama` scaffold + onboarding wizard step | `v0.7.0-γ` |
| release | CHANGELOG + bump + install + dogfood on a fresh greenfield project | `v0.7.0` |

Dogfood target for the release: a new tiny TypeScript service
scaffolded with `lattice init --architecture ama`, with one
real `Features/CapturePayment/` slice, exercising every
structural check and the `.ai-spec.md` emitter end-to-end.
DevelopersPortal stays untouched — it's the brownfield
counter-example proving the checks are opt-in.

---

## 5. Why now

v0.6 made the meaning layer queryable end-to-end. v0.7 makes
the *shape* of the code support that queryability for new
projects. With both in place, an AI agent picking up a feature
loads:

- the `.ai-spec.md` (≤500 words)
- the feature's manifest + RTM row (≤200 tokens)
- the journey for the parent BRD (mermaid, small)
- the feature's own folder (size-capped)

≈ 3–4k tokens, and the agent has the full surface to act on.
That's the AMA promise; Lattice provides the meaning and the
enforcement, AMA provides the shape.
