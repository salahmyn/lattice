# Lattice v0.2.0 — Brownfield Adoption

Document status: design proposal, ready for review
Supersedes: the one-line brief "build all artifacts from an existing project,
add decorations, build the graph; combine static analysis with LLM work."

---

## 1. Premise

v0.1 is a **greenfield** tool: a human writes a manifest, annotates the code,
and Lattice keeps the two in sync. Every existing codebase fails the first
step — there are no manifests and no annotations, so there is no graph.

v0.2 makes Lattice adopt an **existing** codebase: it discovers the features
already latent in the code, drafts their manifests, attaches the code to them,
and produces a knowledge graph that is indistinguishable from a hand-authored
one — that is, it passes the v0.1 validation engine unchanged.

The headline command is `lattice import`.

---

## 2. The core idea: static analysis proposes, the LLM labels, the engine verifies

The original brief — "combine static analysis with LLM work" — is correct but
under-specified. The improvement is to pin down **who is allowed to decide
what**, because static analysis and an LLM fail in opposite directions:

| | Strength | Failure mode |
|---|---|---|
| **Static analysis** | precise, deterministic, re-runnable; knows the call graph, routes, types, tests | cannot *name* a feature or *state* an invariant |
| **LLM** | semantic: naming, prose, judging cohesion, drafting invariants | hallucinates; non-deterministic; invents structure that isn't there |

So the rule is: **static analysis owns all structure; the LLM owns only
labels; the deterministic engine fact-checks the labels.**

- The LLM is **never** asked an open question ("what features exist?"). It is
  asked a **grounded** one: "here are 14 symbols, their call relationships,
  their routes, and their tests — name this feature and state its purpose."
- Every LLM claim is **falsifiable**. If the LLM drafts an invariant, v0.1's
  validator must find its enforcer and verifier in real code; if it can't,
  the claim surfaces as a normal `UNENFORCED_INVARIANT` / `UNVERIFIED_INVARIANT`
  violation. The LLM proposes; the engine disposes.

This is what "generate the artifacts in the correct way" means concretely:
**the bootstrap output is correct iff it survives `lattice validate`.**

## 3. The import pipeline

Five stages. Each is independently runnable; the whole loop is re-runnable and
idempotent.

```
  Discover ──▶ Label ──▶ Decide ──▶ Verify ──▶ Inscribe
  (static)    (LLM)      (human)    (engine)   (writer)
     ▲                                            │
     └──────────────── re-run ────────────────────┘
```

### Stage 1 — Discover (static, deterministic)

Produce **feature candidates** from the code. No names, no prose — only
structure and evidence.

Clustering signals, in rough order of reliability:

- **Harvested metadata** (cheapest, most reliable): existing HTTP-route
  decorators/handlers, event emit/consume sites, OpenAPI/Swagger/JSON-schema
  files, gRPC/proto services, scheduled-job registrations, existing docstrings.
  A codebase already contains latent "meaning" — harvest it before generating
  anything.
- **Module / package structure**: directories and packages are the team's own
  first decomposition.
- **Call-graph cohesion** (from SCIP, already in v0.1): symbols that call each
  other densely and are called from outside as a unit.
- **Shared types**: symbols operating on the same domain types.
- **Test grouping**: a test file exercising a set of symbols implies they form
  a unit, and its assertions are invariant evidence.

Each candidate carries: its symbol set, a **confidence** score, and the
**evidence** that produced it (which signals fired, with specifics). Evidence
is non-negotiable — it is what makes a reviewer able to trust the result.

Output: `lattice/import/candidates.json` (a draft artifact, see §5). Stage 1
runs with **no LLM** and is valuable on its own — it is a structural map of an
unfamiliar codebase.

### Stage 2 — Label (LLM, grounded, cached, with deterministic fallback)

For each candidate, the LLM receives the evidence and returns **only**:

- a feature `id` (dot-nested where the structure implies a hierarchy),
- a `purpose`,
- 1–N capability names + summaries,
- **invariant candidates, each tagged with the specific evidence it rests on**
  (an assertion, a guard clause, a test assertion, a type constraint).

The LLM may not introduce symbols, merge, or split clusters — it labels the
structure Stage 1 found. Outputs are cached by input hash (v0.1 already does
this for agentic capabilities) so re-runs are cheap and stable.

**Deterministic fallback** (v0.1's established pattern): with no LLM
configured, candidates are still emitted as draft manifests with mechanical
names (`candidate_group_3`) and `TODO` prose. Brownfield import must work
air-gapped — the LLM improves names, it is not required for structure.

### Stage 3 — Decide (human)

The reviewer works **one candidate at a time**, never a bulk accept. For each,
Lattice produces a *feature import bundle* (reusing the v0.1 agent-context
bundle shape): the draft manifest, the evidence, the symbols, the tests, the
harvested routes. The reviewer can **accept / edit / merge / split / reject**.
Accepted candidates become real `status: proposal` manifests under
`lattice/features/`.

### Stage 4 — Verify (the v0.1 engine, deterministic)

The accepted manifests plus the planned code↔feature mapping are run through
`lattice validate`. This is the fact-check: an LLM-drafted invariant with no
enforcer in real code fails here. The import is "done" only when its output
validates — green by the same rules a hand-authored repo answers to.

### Stage 5 — Inscribe (the annotation writer — new subsystem, see §4)

Attach the code to the features. Two modes, and this is a deliberate
improvement over the brief:

- **Sidecar mode (default for day one):** write an `annotation-map.yaml` —
  a generated `feature ↔ symbol-FQN` mapping the graph builder merges as if
  the annotations were in code. **Adopting Lattice no longer requires a
  giant code-mod PR.** You get the full graph without touching a line.
- **Inline mode (progressive):** the annotation writer inserts the real
  decorators / JSDoc / attributes into source — preview→apply, idempotent,
  per-language-correct, reversible. Teams "burn down" the sidecar into inline
  annotations at their own pace.

## 4. New subsystem: the annotation writer

v0.1 can *render* an annotation snippet (`RenderAnnotationSuggestion`) but
cannot *write it into a file*. v0.2 needs a real code-modification engine —
the source-code analogue of the v0.1 patch engine.

Requirements:

- **Placement-correct:** insert a Python decorator above the `def`, a JSDoc
  block above the declaration, a PHP attribute above the symbol — without
  breaking syntax.
- **Idempotent:** running it twice changes nothing; re-import after code
  changes does not churn untouched files.
- **Preview → apply:** same two-phase contract as manifest patches.
- **Compile-checked:** after applying, re-parse every touched file with the
  adapter; a syntax break rolls the file back. ("Correctness" includes *the
  build still works*.)
- **Reversible:** an `uninscribe` path removes Lattice annotations cleanly.

The graph builder is extended to merge edges from `annotation-map.yaml` with
in-code annotation edges, so sidecar and inline modes produce the same graph.

## 5. The import session

Brownfield import is not one-shot — the code keeps moving, and a 200k-LOC
repo cannot be reviewed in one sitting. v0.2 introduces a persisted, scoped,
re-runnable **import session**.

```
lattice/import/
├── session.yaml          scope, status, per-candidate decisions
├── candidates.json       Stage-1 output (deterministic, re-buildable)
├── drafts/               Stage-2 draft manifests, pre-acceptance
└── annotation-map.yaml   the generated code↔feature mapping
```

- **Scoped:** `lattice import scan --scope src/billing/` — import one bounded
  context at a time; a 400-feature big-bang is unreviewable.
- **Idempotent:** stable candidate IDs (hashed from the symbol set) so re-runs
  reconcile rather than duplicate; accepted decisions survive a re-scan.
- **Conflict-aware:** before creating a feature, run it through the v0.1
  conflict analyzer so the import does not mint a duplicate of an
  already-accepted feature.

## 6. Coverage: how much of the codebase is adopted

`lattice validate` answers *is the graph correct?* It does not answer *how
much of the code does the graph describe?* Brownfield adoption needs the
second number — the analogue of test coverage, but for **meaning**.

Coverage is reported as **three ratios, never collapsed into one**, because
they answer different questions and become available at different stages:

| Ratio | Numerator ÷ denominator | Available after | Answers |
|---|---|---|---|
| **Discovery** | symbols Stage 1 placed in *some* candidate ÷ all discoverable symbols | `import scan` | how much code has Lattice even looked at? |
| **Documentation** | symbols attached to an *accepted* feature ÷ all discoverable symbols | `import review` | how much code is described by a real manifest? |
| **Verification** | declared invariants with an enforcer *and* a verifier ÷ all declared invariants | `import verify` | how much recorded meaning is fact-checked? |

The verification ratio is just v0.1's existing
`UNENFORCED_INVARIANT` / `UNVERIFIED_INVARIANT` accounting, surfaced as a
percentage instead of a violation list.

**Denominator hygiene.** A coverage percentage is meaningless without its
denominator, so the report always prints it. The symbol universe excludes
vendored, generated, and test code by default (`import.coverage.exclude`
globs) — coverage measures *production* code unless told otherwise.

**Breakdown.** Coverage is reported per code-root and per top-level
package/directory, so a reviewer sees `src/billing 92%` next to
`src/legacy 4%` and scopes the next `import scan --scope` accordingly. The
breakdown *is* the adoption roadmap.

**Report, not gate.** A partial import is still correct — coverage measures
*completeness*, `validate` measures *correctness*, and the two are
orthogonal. But a project may set `import.coverage.min` and have CI fail
below it, the same way teams gate test coverage.

**Deterministic.** Computed from `candidates.json`, the accepted manifests,
and the graph — same inputs produce the same report byte-for-byte.

Surfaced two ways: standalone `lattice coverage`, and folded into
`lattice import status` so session progress always shows a live adoption
percentage.

## 7. CLI surface

```
lattice import scan    [--scope <dir>]   # Stage 1 — discover, no LLM, no writes
lattice import draft   [--scope <dir>]   # Stage 2 — label candidates (LLM or fallback)
lattice import review  [<candidate-id>]  # Stage 3 — per-candidate bundle + accept/edit/reject
lattice import verify                    # Stage 4 — validate the generated substrate
lattice import inscribe [--inline]       # Stage 5 — write sidecar map, or inline annotations
lattice import status                    # session progress + live coverage
lattice coverage       [--scope <dir>] [--by root|package|file]   # adoption %: discovery / documentation / verification
```

All with `--json`. Each MCP-exposable, so an external agent can drive the
import loop the same way it drives the rest of Lattice.

## 8. Definition of "correct"

The import is correct when **all** of these hold — and each is mechanically
checkable, not a matter of opinion:

1. Every generated manifest passes `lattice validate` (schema, dependency,
   verification rules).
2. Every feature maps to at least one real code symbol.
3. Every generated invariant has at least one enforcer; unenforceable
   invariants are demoted to documented candidates, never silently kept.
4. Inline-mode annotations leave every touched file parsing cleanly.
5. Re-running `import scan` on unchanged code reproduces the same candidates
   byte-for-byte (determinism, as v0.1 already guarantees for `extract`).

## 9. Reuse vs. new

**Reused from v0.1 (most of the machinery already exists):**
SCIP call graph (clustering input) · the embedder (dedup similar candidates) ·
the LLM provider abstraction + caching · the conflict analyzer (no duplicate
features) · the validation engine (the Stage-4 fact-checker) · the patch
engine pattern (model for the annotation writer) · the agent-context bundle
(model for the import bundle) · surfaces/errors (harvested routes map straight
onto them).

**Genuinely new in v0.2:**
the discovery/clustering engine · grounded labeling prompts · the **annotation
writer** (code modification) · the sidecar `annotation-map.yaml` and graph-merge ·
the import session.

v0.2 is therefore mostly **orchestration of v0.1 parts** plus one substantial
new component (the annotation writer).

## 10. Risks and mitigations

| Risk | Mitigation |
|---|---|
| LLM cost on a large repo | Stage 1 is LLM-free; LLM runs only on in-scope / accepted candidates; cached by input hash |
| Wrong feature granularity | Reviewer can merge/split; Stage 1 can emit candidates at two granularities (package vs. cluster) |
| Annotation writer breaks the build | Compile-check after apply; rollback; sidecar mode avoids touching code at all |
| Re-run churn | Stable hashed candidate IDs; idempotent insertion; persisted decisions |
| LLM invents unfalsifiable invariants | Stage 4 verification — no enforcer ⇒ violation ⇒ not accepted |
| Unreviewable big-bang | `--scope`; one-candidate-at-a-time review; proposal-status output |

---

## 11. Phasing

- **v0.2.0-α — Discover.** `import scan` + the import session + candidate
  evidence + **discovery coverage**. Pure static analysis; immediately
  useful as a codebase map with an adoption percentage.
- **v0.2.0-β — Label + Decide.** Grounded LLM labeling, deterministic
  fallback, the per-candidate review loop, Stage-4 verification, and the
  **documentation + verification coverage** ratios.
- **v0.2.0 — Inscribe.** The annotation writer: sidecar mode, then inline mode
  with compile-checking.

Each phase ends green against the v0.1 engine and ships independently.

---

## 12. Out of scope for v0.2.0

- Auto-accepting candidates (Lattice proposes; humans decide — unchanged from
  v0.1's stance).
- Inferring initiatives/tasks from git history (a v0.3 idea).
- Cross-repo feature discovery beyond what `workspace.yaml` already declares.
- Languages beyond Python, TypeScript, PHP.
