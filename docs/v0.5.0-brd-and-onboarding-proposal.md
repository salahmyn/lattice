# Lattice v0.5.0 — BRD, onboarding wizard, brand system

Document status: design proposal, ready for review
Supersedes: the post-v0.4.2 ask to "introduce an extra BRD layer (greenfield
+ brownfield LLM regeneration); add an onboarding wizard from CLI to UI;
auto-detect language/framework and install required plugins; apply the
Crystal brand system to the UI."

---

## 1. Premise

After four releases, Lattice has three peer axes (Feature, EntryPoint,
Workspace) and a UI that consumes them. Two layers above and one layer
below remain conspicuously missing for a serious adoption story:

| Layer | What it answers | Today |
|---|---|---|
| **Business intent** | "Why does this exist; who's the buyer; how do we know it worked?" | Implicit in `Feature.purpose` (one sentence) |
| **First-touch flow** | "I just heard about Lattice; what do I do?" | `lattice init` writes empty files; user reads docs to learn what's next |
| **Brand identity** | "Does this look like a serious tool I'd buy / use / commit to?" | Default Tailwind slate; no wordmark; reads like an internal dashboard |

v0.5 closes all three. The headline additions are:

1. **BRD** — Business Requirements Document, a new top-of-stack artifact.
2. **`lattice init` → UI onboarding wizard** — interactive setup, with
   auto-detection of language/framework and one-click plugin install.
3. **Crystal brand system** — cool slate + mica violet, Geist + JetBrains
   Mono, uppercase wordmark with hex unit-cell mark; applied across every
   UI surface from the v0.4 work.

---

## 2. The BRD layer

### 2.1 What a BRD is, in Lattice terms

A BRD captures *business intent* — the layer above the technical feature
manifest. One BRD points at one or many features that implement it; one
feature has at most one BRD parent.

```yaml
# lattice/brds/checkout-refund.yaml
id: brd.checkout.refund
version: 1
status: approved                  # draft | proposed | approved | superseded
title: Customer self-service refunds
business_problem: |
  Customer service handles 1.2k refund requests/day, average 8 min each;
  ~70 % are within return window and could be self-served if the
  storefront exposed a refund path with the right guardrails.
business_goals:
  - Reduce CS ticket volume by 30 %
  - 95 % of eligible refunds complete in <5 min unattended
  - Refund disputes per 1k orders trend flat or down
stakeholders:
  business_owner: payments
  product_owner: checkout-pm
  engineering_owner: checkout-eng
  legal: payments-compliance
user_scenarios:
  - id: refund_within_window
    actor: Customer
    narrative: |
      A customer who placed an order in the last 30 days opens the order
      from their account, taps "Request refund", confirms reason, and
      sees the refund posted to their original payment method.
  - id: partial_refund
    actor: Customer
    narrative: Same flow, but they refund one item from a multi-item order.
success_criteria:
  - { id: SC-1, statement: "Refund never exceeds original charge",
      maps_to_invariant: "checkout.refund:INV-1" }
  - { id: SC-2, statement: "Refund issued within 5 min of approval" }
  - { id: SC-3, statement: "EU customers pass SCA before refund approval" }
constraints:
  - { kind: regulatory, ref: PCI-DSS, note: "Card data handled" }
  - { kind: regulatory, ref: PSD2-SCA, note: "EU transactions" }
out_of_scope:
  - Refunds for items shipped >90 days ago
  - Currency conversion at refund time
implements_via:                   # forward link to the feature axis
  - checkout.refund
  - payments.gateway.charge_reversal
approval:
  approved_by: pm@example.com
  approved_at: 2026-05-20T00:00:00Z
  approved_version: 1
provenance:
  source: human                   # or: llm_from_code
  generated_at: ""                # set only for llm_from_code
```

`Feature` gains exactly one new field: `implements_brd: brd.checkout.refund`.
The relationship is one-to-many BRD → Feature; bidirectional navigation
is via the existing graph build pass (same shape as EP-reached-by-feature).

### 2.2 LLM regeneration for brownfield

`lattice brd from-code <feature-id>` (and `--all-unbrided` for bulk)
generates a draft BRD from:
- the feature's manifest (purpose, capabilities, invariants, owners),
- its implementations + reached-by entry points (from the v0.3 inverse
  flow),
- the v0.2.1 tone contract for voice.

The LLM is allowed to draft `business_problem`, `business_goals`,
`stakeholders` (inferred from `Owners`), `user_scenarios` (from EPs +
capability rules), `success_criteria` (from invariants).

The LLM is explicitly forbidden from inventing `constraints` (regulatory,
legal) — those are left as `[]` with a `# TODO: legal review` comment.
Brownfield-generated BRDs land as `status: draft, provenance.source:
llm_from_code, human_review_required: true`.

### 2.3 Validation rules

| Code | Severity | Trigger |
|---|---|---|
| `BRD_PHANTOM_FEATURE` | error | `implements_via` names a non-existent feature |
| `BRD_UNREFERENCED` | info | BRD has no `implements_via` — usually a draft |
| `FEATURE_NO_BRD` | warning | Feature has no upstream BRD (incremental adoption — never error) |
| `BRD_DRIFT` | info | `feature.version > brd.approved_version` — BRD may be stale |
| `BRD_UNAPPROVED_LLM` | warning | LLM-generated BRD still in `draft`; needs human sign-off |

All deliberately conservative — adoption is opt-in.

### 2.4 CLI + UI

```sh
lattice brd new <id>                       # scaffold
lattice brd list [--status draft|...]
lattice brd show <id>
lattice brd link <brd-id> <feature-id>     # writes back to feature manifest
lattice brd approve <id> --by <email>      # sets approval block
lattice brd from-code <feature-id>
lattice brd from-code --all-unbrided
```

UI: `/brds` (table grouped by status), `/brds/{id}` (full manifest +
linked features + drift indicator), Coverage dashboard gains a 4th
ratio — **BRD coverage** = features-with-approved-BRD ÷ features.

## 3. The onboarding wizard

### 3.1 Two-surface flow

`lattice init` is no longer a one-shot scaffold. It becomes the **first
half** of a two-step setup, with the **second half** in the UI:

```
$ lattice init
Detecting your project…
  language: PHP 8.2  (composer.json)
  framework: Laravel 10  (composer.lock + bootstrap/app.php)
  code roots: app/, Modules/, vendor/salla/  (suggested)

Scope of this project?
  1. Greenfield — I'll write BRDs/features as I build new things.
  2. Brownfield, full — generate everything from the existing code.
  3. Brownfield, incremental — track only new BRDs/features going forward.
> 2

I'll need: scip-php, infection. Install now? [Y/n] y
  $ composer global require sourcegraph/scip-php infection/infection

Workspace initialised at lattice/. Continue setup in the browser:
  lattice serve --open
```

`lattice serve --open` (new flag) launches the server and opens the
browser at `/onboarding`. The UI picks up where the CLI left off via
`lattice/onboarding.yaml`:

```yaml
version: 1
step: brand_metadata               # current step
scope: brownfield_full             # from CLI step 1
detected:
  language: php
  framework: laravel
  code_roots: [app, Modules, vendor/salla]
  packages_installed: [scip-php, infection]
needs_review: [tone, owners, first_brd]
```

### 3.2 Steps in the UI wizard

1. **Project metadata** — title, owners (default from `git config user.email`),
   default tone (audience + reading level).
2. **Confirm code roots** — UI shows detected roots with file counts; user
   can add/remove.
3. **Adapter & plugin status** — green if installed, "Install" button if
   missing. Posts to `POST /api/v1/install` which runs the right
   package-manager command in a subprocess.
4. **Scope-specific path:**
   - **Greenfield:** "Create your first BRD" form → writes
     `lattice/brds/<slug>.yaml`. The system then schedules the engineer
     to draft features under it.
   - **Brownfield-full:** runs `lattice import scan` + `import draft` +
     `brd from-code --all-unbrided` in sequence, streaming progress over
     SSE (the v0.4.2 channel). Reviewer is dropped on `/import` to
     accept/reject candidates and `/brds` to sign off draft BRDs.
   - **Brownfield-incremental:** skips bulk import; explains that new
     features should be added through `lattice brd new` + `lattice
     feature new`.
5. **Done** — onboarding.yaml gets `completed: true`; the wizard
   redirects to `/`.

Re-running `lattice init` after completion is idempotent: shows current
state, lets the user re-trigger any step.

## 4. Auto-detect language/framework + install plugins

New `pkg/lattice/detect` package walks the repo and scores languages +
frameworks. Scoring is signal-stack: presence of a manifest file
(`composer.json`, `package.json`, `requirements.txt`, `go.mod`) plus
the framework's signature directories or imports (Laravel's
`bootstrap/app.php`, Django's `manage.py`, FastAPI's `from fastapi
import FastAPI`).

Output:

```go
type Detection struct {
    Language     string    // php | python | typescript | javascript | go
    Framework    string    // laravel | symfony | django | flask | fastapi | express | nest | none
    Confidence   float64   // 0.0–1.0
    CodeRoots    []string  // suggested
    NeedsPackages []Package // {name, install_cmd, reason}
}
```

`Package.install_cmd` comes from the existing `adapters/*` install hints
(`composer global require sourcegraph/scip-php`, etc.) plus mutation
runners (`pip install mutmut`, etc.) and the MCP server
(`npm i -g @salahmyn/mcp-server`).

CLI:

```sh
lattice detect            # print the report
lattice detect --install  # runs the install commands (with confirmation)
```

UI calls `lattice detect --json` server-side during onboarding step 3
and surfaces a per-package "Install" button.

### 5.4 Typography

- **Sans:** Geist (300/400/500/600/700), with system fallback.
- **Mono:** JetBrains Mono (400/500/600/700) for all code/FQNs/IDs.
- **Serif:** IBM Plex Serif (400/500/600) reserved for long-form
  business prose like a BRD's `business_problem`.

8-step scale, 4-px base spacing system, radius `xs:2 sm:3 md:4 lg:8`.

### 5.5 Wordmark + mark

- **Wordmark:** `LATTICE` — uppercase, Geist 600, tracked `0.18em`,
  mica-400 accent on the dot of the `I`.
- **Mark:** `⬡` (hex unit cell) — the Feature primitive glyph
  doubled-up at logo scale. Used solo in tight spaces, paired with
  wordmark in nav headers.

## 6. Reuse vs. new

**Reused:**
- v0.2 importer (brownfield drives BRD generation in bulk).
- v0.3 entrypoints (BRD `user_scenarios` cite EPs).
- v0.4 server + JSON API shape (BRD endpoints follow the same
  conventions: `/api/v1/brds`, `/api/v1/brds/{id}`).
- v0.4.1 reflect-form (BRD edit form is generated automatically).
- v0.4.2 SSE (onboarding progress streams over the same channel).

**Genuinely new:**
- `pkg/lattice/schema/brd.go` — BRD struct + load/save.
- `pkg/lattice/brd/` — LLM regeneration + validation rules.
- `pkg/lattice/detect/` — language/framework detection.
- `internal/cli/brd.go` + `internal/cli/detect.go` + `internal/cli/wizard.go`.
- `pkg/lattice/ui/onboarding.go` + templates.
- `assets/static/crystal.css` — the brand system applied.

## 7. Phasing

- **v0.5.0-α — Brand.** Crystal applied to every existing UI page; new
  wordmark/footer. No new features; visual identity only.
- **v0.5.0-β — BRD.** Schema, CLI, validation, UI. Manual BRD authoring
  works end-to-end.
- **v0.5.0-γ — `brd from-code`.** LLM regeneration with the tone
  contract and explicit constraint-forbidden prompts.
- **v0.5.0-δ — Onboarding wizard + auto-detect.** `lattice init`
  becomes interactive; UI wizard takes over; `lattice detect [--install]`
  resolves and installs missing prerequisites.

Each phase ships independently against the v0.4 engine.

---

## 8. Out of scope for v0.5.0

- BRD signing with cryptographic identity (just the `approval` block).
- Workflow / approval-routing (no PR-style review queues; humans use
  git review on the YAML file).
- Multi-language BRDs (single locale per BRD; teams duplicate if needed).
- OIDC for the onboarding wizard's install step (the install runs
  client-side with the user's shell credentials).

---

## 9. Definition of "done"

1. Every page under `lattice serve` renders in the Crystal palette with
   Geist + JetBrains Mono, dark by default.
2. `lattice brd new` → `lattice brd link` → `lattice brd approve`
   round-trips an authored BRD into the validation cascade.
3. `lattice brd from-code <feature>` produces a `status: draft`,
   `provenance.source: llm_from_code` BRD that the validator surfaces
   as a `BRD_UNAPPROVED_LLM` warning until approved.
4. `lattice init` on a Laravel repo detects Laravel, prompts for scope,
   offers to install scip-php + infection, and writes onboarding.yaml.
5. The UI `/onboarding` page picks up the same `onboarding.yaml` and
   walks the user through the remaining steps.
6. `lattice detect --install` resolves and installs every missing
   package the configured adapters need.
