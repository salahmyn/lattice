# Lattice v0.4.0 — UI: tracking, visualising, navigating, configuring

Document status: design proposal, ready for review
Supersedes: the post-v0.3 ask to "start building the UI that helps tracking,
visualizing and navigating the artifacts and modifying the configuration."

---

## 1. Premise

Lattice today is CLI + MCP. Two surfaces, both terminal-bound. Three audiences
the CLI serves poorly:

| Reader | Today's path | Friction |
|---|---|---|
| Product / business reviewer | reads YAML in an editor, runs `lattice view business` | reads YAML, runs CLI |
| Engineer browsing a new codebase | `lattice feature show`, `lattice search`, paste Mermaid into a viewer | terminal-only, no click-through |
| Operator changing config | edits `lattice/config.yaml` by hand, re-runs commands | no schema awareness, no live preview |

v0.4 adds a **web UI** that consumes the exact same artefacts the CLI produces
— `lattice.json`, `lattice/features/`, `lattice/entry-points/`, `lattice/import/` —
and lets non-CLI users do the read-only flows entirely through a browser, plus
gives engineers a faster navigate-search-visualise loop, plus gives operators a
schema-aware config editor.

The headline command is `lattice serve`.

---

## 2. Tech choices

Five hard constraints, each pinning one decision:

1. **Single binary, no new runtime.** The user already installs Lattice as a Go
   binary; the UI must not require Node, Electron, or a separate process. →
   **Backend = Go `net/http` stdlib; frontend assets are `go:embed`-bundled**.
2. **No build pipeline for the frontend.** A change to the UI must land via
   `go build` only — no npm install, no Vite. → **Server-rendered Go templates
   + a sprinkle of vanilla JS for interactivity.** Heavier widgets (search,
   diagrams) use CDN-loaded libraries that need no compile step.
3. **The CLI is the source of truth.** Every UI page reads through the same
   `buildGraph()` the CLI uses; no parallel data path. → JSON API endpoints
   wrap CLI builders; templates render the same shapes the CLI prints.
4. **Localhost-default, opt-in remote.** The UI ships behavioural data and
   exposes a config editor. → Bind to `127.0.0.1` by default; expose `--host`
   only if the user also supplies `--token <secret>`.
5. **The graph is the model.** No new schemas. The UI navigates exactly the
   types in `pkg/lattice/schema`. → Pages are views over `KnowledgeGraph`,
   not over a UI-specific model.

Picks:
- **Server**: Go 1.22 `http.ServeMux` (pattern matching), embedded templates
  via `html/template`, embedded assets via `embed.FS`.
- **CSS**: Tailwind via CDN (Play CDN, no build) — utility-first matches the
  "no build step" rule. Fall-back hand-rolled CSS file embedded for offline.
- **JS**: vanilla. `Alpine.js` (8KB minified) loaded from CDN for declarative
  client-side state. No bundler, no React.
- **Diagrams**: Mermaid via CDN — we already emit Mermaid from the CLI.
- **Search**: server-side over `KnowledgeGraph`; client renders results.

## 3. Pages

```
/                              overview (workspace, counts, last extract)
/features                      table: all features with status, owners, impl count
/features/{id}                 detail: manifest + impls + tests + reached-by EPs
/entry-points                  table by kind (HTTP / CLI / cron / queue)
/entry-points/{id}             detail: trigger, handler, flow, side-effects
/flows/{ep-id}                 Mermaid flowchart for one entry point
/coverage                      v0.2.1 dashboard (discovery / doc / verification)
/validation                    violations grouped by code, next_action chips
/import                        candidates list with per-candidate mode + decision
/import/{candidate-id}         bundle: evidence, symbols, draft manifest
/config                        form-based editor: config.yaml + workspace.yaml
/search?q=<term>               results across features/caps/invariants/EPs/symbols
```

Every page has a global header with breadcrumbs, a search bar, and a "JSON"
link that exposes the same content as `--json`.

## 4. JSON API

The same shapes the CLI emits via `--json`, routed under `/api/v1/`:

```
GET  /api/v1/overview            workspace + counts + last_extract
GET  /api/v1/features            list (paginated)
GET  /api/v1/features/{id}       single feature (manifest + edges)
GET  /api/v1/entry-points        list
GET  /api/v1/entry-points/{id}   single EP (trigger + handler + flow)
GET  /api/v1/coverage            three coverage ratios + per-package
GET  /api/v1/validation          violations
GET  /api/v1/search?q=           full-text search
GET  /api/v1/config              parsed config.yaml + schema
PUT  /api/v1/config              writes new config (validated before save)
GET  /api/v1/workspace           workspace.yaml
PUT  /api/v1/workspace           writes
GET  /api/v1/import/candidates   importer.CandidatesFile
GET  /api/v1/import/drafts/{id}  one draft manifest
POST /api/v1/import/decisions    apply a batch decisions payload
```

Mutation endpoints (`PUT`/`POST`) require either localhost OR a valid token
header (`X-Lattice-Token`).

## 5. Security

- Default bind: `127.0.0.1:7070`. No token required because the loopback
  interface is unreachable from the network.
- `--host 0.0.0.0` (or any non-loopback) fails to start unless `--token <X>`
  is also passed. Every request must carry `X-Lattice-Token: <X>` or comes
  back 401.
- Static assets and read-only API endpoints are token-gated on non-loopback;
  read-only and writes use the same gate (no escalation surface).
- No cookies, no sessions; tokens are pre-shared. Production deployments are
  expected to put a reverse proxy in front for OIDC, mTLS, etc — out of
  scope for v0.4.0.

## 6. Configuration editor

The most opinionated piece. v0.4.0 ships a **schema-driven** form generator:

- Each top-level `config.yaml` section (`agentic`, `import`, `knowledge`,
  `mutation_testing`, ...) becomes a collapsible card.
- Each field becomes a labelled input whose type comes from the Go struct
  field type (bool→checkbox, string→text, int→number, enum→select).
- A `// help: ...` comment on the Go struct field becomes the field help text
  (read via a small `reflect`-based introspector at startup).
- Submit POSTs the rebuilt YAML; the server parses it through `config.Load`
  and rejects on any schema error before writing.

The same approach powers a workspace.yaml editor (code roots add/remove).

A "preview diff" panel shows the YAML the form would write before the user
clicks Save — no surprise overwrites.

## 7. Import session UI

Reviewing 50–500 candidates is the dominant brownfield-adoption workload.
v0.2.1 made the CLI loop bearable; v0.4 makes it a UI:

- **Candidates table**: paginated by 50. Columns: id, package, confidence,
  symbol count, mode tag (LLM/cached/fallback from v0.2.1), decision.
- **Filters**: scope (multi-select on packages), mode, decision, where-style
  predicates from v0.2.1 `--where` expressions.
- **Per-row action**: hover row to reveal Accept / Reject / View bundle.
- **Selection toolbar**: Accept All Selected / Reject All Selected, with the
  decision applied via the v0.2.1 batch path.
- **Bundle panel**: clicking a candidate slides in the bundle — evidence,
  symbols, draft manifest YAML side-by-side with the candidate metadata.
- **Re-draft control**: re-run the labeler for one or many candidates with a
  different tone (e.g. switch audience for selected rows without touching
  config).

## 8. Visualisations

Three v0.4.0 viz primitives, each backed by a JSON endpoint:

1. **Flow** — Mermaid flowchart, one per entry point, with click-through:
   nodes are anchored to feature/EP detail pages.
2. **Feature tree** — Mermaid graph of `id` hierarchy (`accounts` →
   `accounts.api` → `accounts.api.wrappers.subscription`). Click navigates
   to that feature's page.
3. **Dependency graph** — Mermaid graph of `depends_on` edges across all
   features. Filterable to "show only what touches feature X".

A future v0.4.1 could add:
- Per-module coverage heatmap (treemap with discovery % colouring).
- Per-entry-point call-graph depth chart.

## 9. Reuse vs. new

**Reused from v0.1–v0.3**:
- `buildGraph()` for every read path (the CLI and the UI render the same
  in-memory graph).
- The validation engine (`/validation` is the same `Validate()` output).
- The importer (`/api/v1/import/*` proxies the same calls the CLI commands
  invoke).
- Mermaid rendering for flows (the same `views.RenderFlows` text).

**Genuinely new in v0.4**:
- `lattice serve` CLI command.
- `pkg/lattice/ui/` — HTTP server, embedded assets, JSON API, templates.
- Form-driven schema-aware config editor.
- Live import session UI.

## 10. Phasing

- **v0.4.0-α — Server skeleton + read-only views.** `lattice serve`, JSON
  API for overview/features/entry-points, the home + features list + feature
  detail + entry-points list + entry-point detail pages, Mermaid flow
  rendering. No editing yet.
- **v0.4.0-β — Navigation + search + dashboards.** Search bar across all
  artefact types, click-through everywhere, coverage and validation
  dashboards.
- **v0.4.0-γ — Config editor + import session UI.** Schema-driven form for
  config.yaml + workspace.yaml, candidates table with inline accept/reject,
  bundle drawer, batch toolbar.

Each phase ends with the server up against DevelopersPortal and a working
flow demonstrated.

---

## 11. Out of scope for v0.4.0

- Real-time updates (websocket push when a file changes) — manual refresh
  is fine for the first release.
- Authentication beyond pre-shared token (no OIDC, no users/roles).
- Theme / dark mode beyond Tailwind's prefers-color-scheme default.
- Mobile layouts — Lattice's audience uses laptops.
- A REST API stable contract — `/api/v1/` is internal until v0.5.

---

## 12. Definition of "done"

v0.4.0 is shippable when **all** of these hold:

1. `lattice serve` runs against any v0.3.x workspace and renders the seven
   alpha-phase pages without errors.
2. Every page has a working "JSON" link that returns parseable JSON.
3. The config editor round-trips a `config.yaml` byte-for-byte when no
   field is changed (determinism — same property `lattice extract` honours).
4. The import session UI's bulk accept matches the CLI bulk path
   byte-for-byte on the same input.
5. Non-loopback bind without `--token` refuses to start.
6. `go build` is the only build step.
