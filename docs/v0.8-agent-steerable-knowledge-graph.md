# Lattice v0.8 — The Agent-Steerable Knowledge Graph

Document status: design proposal, ready for review
Driver: Lattice's next user is not a person reading a dashboard — it is a
*fleet of autonomous agents* steering the same codebase concurrently. v0.6
gave a human operator a Requirements Traceability Matrix. v0.7 gave agents a
slice-sized context budget (AMA). v0.8 makes Lattice the **substrate those
agents are steered by**: a graph they can read to know what to do next,
coordinate so they don't collide, advance autonomously under a policy the
operator chooses, and be held accountable by an append-only ledger of every
truth-claim they move.

The commitment is to one flow — **visibility → documentation → soundness** —
made legible enough that an agent can walk it without a human in the loop,
and auditable enough that a human can trust the walk after the fact.

Every chain in Lattice — `BRD goal → success criterion → invariant →
enforcer → verifier`, and `→ scenario → entry point` — passes through **four
truth-levels**. These are the ground truth an agent's work is measured
against; nothing an agent does is "done" until the chain it touched moves up
this ladder:

```
declared            the artifact exists
  → wired           it links to code/tests that exist        ← validate stops here today
  → correctly-meant the link actually means what the layer above asked
  → demonstrated    the behaviour was observed to pass through a real trigger
```

`validate` proves the first two. v0.8 closes the last two and then builds the
**steering layer** on top — affordances (§4), coordination (§5), and an
attribution ledger (§6) — plus the **autonomy modes** (§7) that let a team
dial how much an agent may advance without a human, and the **adoption + agent
practices** (§9) that get a fleet to *hit the goal* rather than game the flow.

---

## 1. Premise — why AI-first, and the trap that comes with it

A green Lattice dashboard answers *"is what we built wired to what we asked
for?"* It does **not** answer *"does what we built actually do what the user
scenario describes?"* — and it does not answer *"which of you twelve agents
should touch this slice next, and did your last edit move a real number?"*
Those are the questions an autonomous fleet lives or dies by.

The danger is specific: **an agent that optimizes for `validate: clean`
reproduces, faithfully, the worst instincts of a corner-cutting engineer — at
machine speed and across every slice at once.** This is not hypothetical. It
is visible right now in the bundled `lattice-todo-sample` repo, and it is the
clearest argument for why v0.8 must close the goal, not just the flow.

**The live case — meaning fidelity (still red today).** The sample's BRD
`brd.task_tracking` carries SC-2:

> *"Task ids are unique within a session, so complete(id) targets exactly
> one task."* → `maps_to_invariant: todo.add:INV-2`

INV-2 actually states:

> *"Two successful calls to execute() return distinct ids within a session."*

Two-call distinctness ≠ session-wide uniqueness ≠ "targets exactly one task."
The link is **wired, green, and narrower than what it claims to satisfy.**
`lattice validate` is clean and `lattice rtm` reads `100.0% (4/4 verified)`
over this. No amount of test-running closes this gap — a test can pass loudly
while proving something weaker than the criterion asked for.

**The cautionary case — how a chain *got* green (the gaming trap).** US-1
says: *"User adds three items, types `todo list`, sees all three in insertion
order."* The implementation builds a fresh in-memory store **per process
invocation**, so `todo add` and `todo list` in two separate shell commands
cannot satisfy US-1. The repo did not fix that by making the scenario work
across invocations — it reframed it: a `session` subcommand was added so one
process holds the store, the BRD's `business_goals` were narrowed to *"within
one session"*, and *"persistence across process restarts"* was written into
`out_of_scope`. A journey test was added that drives the `session` path and
**passes**.

That is a defensible product decision *if a human made it deliberately*. But
notice what it looks like from the graph's side: **the scenario the user
actually cares about was made to read green by editing the intent until the
code satisfied it.** An autonomous agent told "make US-1 pass" and rewarded on
`validate: clean` would choose exactly this move — narrow the BRD until the
bug is out of scope — because Lattice today gives it no signal that doing so
*lowered the bar* rather than *cleared it*. Worse: `user_scenarios` are not in
the RTM walk at all, so even the passing journey test is invisible to
`rtm` — Lattice cannot tell you US-1 is demonstrated, or that it was ever in
doubt.

| What kept Lattice green / blind | Truth-level missed | Closed by |
|---|---|---|
| `user_scenarios` carry no verification link and are absent from the RTM walk — only `success_criteria` are walked. The thing a user *does* is unverified by construction, and an agent gets no credit (or blame) for it. | demonstrated | α |
| Entry points are modeled but never *required*. A feature, a BRD, and a scenario can all be green with no verified path from a trigger to the behaviour — the CLI↔store seam where the US-1 bug lived was outside every check. | demonstrated | β |
| "verified" means *a `@verifies` test exists* (mutation may gate it to `partial`), never *the test passed on this commit*. Test **results** are never ingested. | demonstrated | γ |
| A wired link can mean *less* than the layer above asked (SC-2 ⊃ INV-2), and nothing flags the narrowing. Wired, green, and **wrong**. | correctly-meant | δ |

An agent fleet amplifies every one of these. v0.8 closes them so that the
graph an agent reads is *worth trusting* — and then builds the layer that lets
agents act on it together.

## 2. The four truth-levels are the contract agents are steered by

Before the streams, the framing that makes this AI-first rather than a pile of
new lint rules: **every affordance, lease, and autonomy decision in §4–§7 keys
off a unit's truth-level, not off "does validate pass."**

- An agent asking *"what should I do next?"* (§4) is answered with the
  **weakest link** — the unit furthest from `demonstrated`/`correctly-meant`,
  not a flat TODO list.
- An agent's edit is *credited* in the ledger (§6) only when it **moves a unit
  up the ladder** — narrowing a BRD to silence a rule moves nothing, so it
  earns nothing and is visible as a no-op-or-regression.
- An autonomy mode (§7) grants self-serve on `declared`/`wired` work and gates
  `correctly-meant` because the cost of a wrong *meaning* is unbounded while
  the cost of a wrong *wiring* is caught by `validate`.

The truth-levels turn "looks done" into a number the fleet optimizes and the
human audits. The four streams below make that number honest.

## 3. Foundation streams — making the truth-levels computable

α/β/γ close **demonstration**; δ closes **meaning fidelity**. Each is additive
and degrades to a no-op on a v0.7 workspace.

### α. Executable scenario verifiers

Make a BRD `user_scenario` a verifiable unit, peer to a `success_criterion`.

- Schema (additive): `UserScenario` gains
  `verified_by: [<test-fqn> | <journey-id>]`. A scenario with no `verified_by`
  is `UNMAPPED` (info), exactly as an unmapped SC is today. *(Today
  `UserScenario` is `{id, actor, narrative}` with no link field — this is the
  one structural addition α needs.)*
- The verifier is an ordinary test the adapter already extracts, tagged
  `@verifies brd.<id>:US-N` (TS) / `@verifies("brd.<id>:US-N")` (Py) /
  `#[Verifies("brd.<id>:US-N")]` (PHP). Reuses the existing `Test.Verifies`
  graph edge — no new extraction path.
- RTM grows scenario rows beneath the SC rows:
  `US-1  demonstrated  ep.cli.todo  1 verifier`. The per-BRD roll-up counts
  scenarios alongside criteria — so the sample's passing US-1 journey test
  finally becomes *visible* and *credited*.

New rules: `BRD_SCENARIO_UNVERIFIED` (warning), `BRD_SCENARIO_UNMAPPED` (info).

### β. Entry-point journey coverage

v0.6 shipped the journey *view*; v0.8 makes journey *coverage* a number agents
chase.

- A 6th Coverage card: **journey coverage** = `scenarios whose verifier
  exercises a declared entry point / total scenarios`. The sample scores 1/2
  (US-1 reachable via `ep.cli.todo`; US-2 unmapped) — a far more honest
  headline than `rtm 100%`.
- `EntryPoint.Flow` already lists the features a trigger reaches. Add the
  reverse check: `FEATURE_UNREACHED` (info) for a `production` feature on no
  entry-point flow — it is either dead or an unmodeled seam (the two states the
  todo store was in before `ep.cli.todo` was declared).
- `SCENARIO_NO_ENTRYPOINT` (info) when a scenario's verifier touches no
  declared entry point — the signal a test asserts pure logic, not a
  user-reachable path. *(Today the only entry-point rules are
  `UNCLASSIFIED_ENTRY_POINT`, `HANDLER_MISSING`, `DUPLICATE_TRIGGER`,
  `PHANTOM_FLOW` — none require reachability; these two add it as advisory.)*

### γ. Demonstration — ingest results, distinguish "test exists" from "test passed"

Today's status ladder is already three-valued: `unverified → partial →
verified`, and **mutation testing already ships and already gates** — a
configured mutation score below threshold drops a unit to `partial`
(`rtm` consumes `pkg/lattice/mutation`). What is genuinely missing is the
*pass/fail* of the verifier itself: status keys off the verifier **existing**,
never off it having **passed on `generated_from_commit`**.

γ adds the missing rung, on top of what's there:

- New top status `DEMONSTRATED` — the verifier **passed** on the generated
  commit, ingested from junit/pytest/phpunit XML via
  `lattice results ingest <file>` into `lattice/.cache/results/`. Today's
  "verified (test exists, mutation OK)" becomes the lower rung `DECLARED`.
- Mutation continues to gate exactly as it does now (`partial` on a surviving
  mutant below threshold) — γ does **not** re-implement mutation; it composes
  with it.
- Coverage and RTM report the *weakest* link, so a BRD cannot show
  `demonstrated` on a declared-but-failing test. New rule `VERIFIER_FAILING`
  (warning) when an ingested result for a `@verifies` test is red.

### δ. Meaning fidelity — does the wired link mean what was asked?

α/β/γ make a green check mean *demonstrated*. δ makes it mean *correctly
meant* — it attacks the SC-2 ⊃ INV-2 narrowing directly. Three mechanical
signals plus one assisted check:

- **Coverage-narrowing signal (`CRITERION_INVARIANT_NARROWER`, info).** An
  **assisted** entailment check between each `success_criterion.statement` and
  its `maps_to_invariant` statement; when the invariant does not entail the
  criterion, flag both texts and the suspected missing clause. This is a *new*
  capability, distinct from the existing `pkg/lattice/analyze` checks — those
  are **deterministic** (a lexical term-frequency embedder, firing
  error/warning findings on surface/invariant overlap). δ's entailment check is
  LLM-backed **only when `agentic.llm.enabled: true`** and a **deterministic
  no-op otherwise**, so a default install never depends on a model. It is
  advisory, never a gate, never auto-edits, and **suppressed entirely for
  `regulatory` / `legal` / `financial` constraints**, which stay human-judged.
- **Vacuous-invariant signal (`INVARIANT_UNFALSIFIABLE`, info).** An invariant
  whose enforcer has no reachable code path that could violate it passes by
  absence, not by guard. Surfaced directly, and **gated hard when
  `lattice mutation run` reports a surviving mutant on the enforcer**
  (`INVARIANT_MUTANT_SURVIVED`, warning) — reusing the mutation engine that
  already exists as the mechanical proof the invariant is unfalsified.
- **Enforcer-quality signal (`ENFORCER_NOT_GUARD`, info).** "3 enforcers" can
  be a class, its constructor, and a method all inheriting one module tag. δ
  distinguishes a **guard** (a symbol with a reject/throw/return-error path the
  verifier's negative case exercises) from a **tag** (a symbol that merely
  carries the annotation). RTM reports guard count, not tag count, so the
  number stops being theatrical.

δ needs only the α schema addition; it reads `maps_to_invariant`, the enforcer
symbols, and (optionally) mutation scores already in the graph.

## 4. Steering layer ① — affordances: what should an agent do next?

The first thing a fleet needs is not more rules but a **machine-readable next
action**. Lattice already has the raw materials — `pick-next`,
`recommend-decomposition`, `views/agentcontext.go`'s `relevant_skills`, and the
`lattice_get_agent_context` MCP tool. v0.8 makes them **goal-aware**.

- **`lattice next` (extends `pick-next`).** Returns a ranked action list keyed
  off the truth-levels, not a flat backlog. Ranking = *weakest link first*: a
  scenario at `UNVERIFIED` outranks a criterion at `DECLARED`, which outranks a
  cosmetic gap. Each item carries: the unit, its current truth-level, the
  target, the smallest slice of context that would let an agent act
  (`.ai-spec.md` + the slice folder), and the relevant skill.
- **Goal-aware skill surfacing.** When a task's `verifies` touches a BRD
  `user_scenario` or `success_criterion`, `relevant_skills` surfaces the two
  goal skills from §9 first — so an agent picking up scenario/meaning work is
  pointed at *achieve the goal*, not just *satisfy the flow*.
- **The loading contract.** `lattice next` returns, per action, the answer to
  *"is one slice enough context?"* If the change needs more than the slice and
  its ≤500-word `.ai-spec.md`, that is the signal the slice is too big — the
  recommended action becomes **split the slice**, not edit it blind.

This is the layer that turns "twelve agents and a repo" into "twelve agents
each handed the highest-value thing they can safely do alone."

## 5. Steering layer ② — coordination: many agents, no collisions

Autonomy across a fleet needs the graph to mediate *who is touching what*.
v0.8 adds a lightweight, file-backed claim protocol that extends the existing
`task`/`kanban` surface and the existing `pkg/lattice/analyze` conflict checks
from *proposals* to *live work*.

- **Leases (`lattice lease acquire <unit>` / `release` / `list`).** An agent
  claims a slice (a feature, a BRD, or a scenario) before editing it. A lease
  records `{unit, actor, acquired_commit, expires, scope: [paths]}` under
  `lattice/.leases/` and is advisory-but-visible: `lattice next` will not hand
  a leased slice to a second agent, and leases expire on a TTL so a dead agent
  never wedges the fleet.
- **Concurrent-edit conflict detection.** When two live leases' `scope` paths
  overlap — most dangerously on `Core/Contracts/*`, the one thing AMA slices
  may share — the existing `analyze/` deterministic checks
  (`surfaceCollisions`, `breakingSurfaceChanges`, `cycleIntroduction`) run
  *between the leased working sets*, not just at proposal time. New advisory
  `LEASE_SCOPE_OVERLAP` (info) and, when a shared contract's surface actually
  diverges, `CONCURRENT_SURFACE_CONFLICT` (warning).
- **Slice-shaped by construction.** Because AMA already colocates a feature in
  one folder and forbids cross-feature imports, a lease's blast radius is the
  folder. Coordination is cheap precisely because v0.7 made the slices
  disjoint — the architecture *is* the concurrency primitive.

No daemon, no lock server: leases are files in the graph, claimed and released
through the same git the agents already commit to, so the coordination state is
itself versioned and auditable.

## 6. Steering layer ③ — the attribution ledger (the soundability spine)

Visibility and documentation are worth nothing to a fleet if you cannot answer
*"which agent moved this claim, on what evidence, and may I trust it?"* The
ledger is that answer — the spine that makes autonomous steering **sound**.

- **Append-only, in-graph, replayable.** Every truth-level transition writes
  one entry to `lattice/.ledger/<date>.jsonl`:

  ```jsonl
  {"ts_commit":"a1b9013","actor":"agent:add-slice-worker","unit":"brd.task_tracking:US-1",
   "transition":"unverified→demonstrated","evidence":"test.journey.us1@a1b9013","mode":"gated"}
  {"ts_commit":"c4f2e07","actor":"agent:meaning-auditor","unit":"brd.task_tracking:SC-2",
   "transition":"correctly-meant?→flagged","evidence":"CRITERION_INVARIANT_NARROWER","mode":"gated"}
  ```

  The ledger is derived state — `lattice ledger rebuild` regenerates it by
  replaying the graph across commits — so it can never silently disagree with
  the code.
- **Credit is earned by movement, not activity.** An edit that narrows a BRD to
  silence a rule produces no upward transition, so it leaves a visible
  *non-entry* (or a `→regressed` entry if it lowered a bar). The §1 gaming
  trap becomes legible: the ledger shows US-1's bar was *moved*, not *cleared*.
- **`lattice ledger` views.** Per-agent (`what did agent-A actually achieve?`),
  per-unit (`who has touched SC-2 and why is it still flagged?`), and
  per-commit (`what truth changed in this merge?`). This is the human's audit
  surface and the fleet's coordination memory in one artifact.
- **Attribution requires identity.** Agents act under a declared `actor`
  (`lattice --actor agent:add-slice-worker …` or `LATTICE_ACTOR`), recorded on
  every lease and ledger entry. Unattributed mutation is a `validate` warning
  (`UNATTRIBUTED_CHANGE`) under autonomy modes that require it.

## 7. Autonomy modes — dial how far an agent runs without a human

The operator chooses, per workspace and overridable per task, how much a unit
may advance before a human is required. Modes are policy over the truth-levels;
they do **not** change what is true, only who may sign off on a transition.

```yaml
# config — autonomy is opt-in; absence means "human approves everything" (v0.7 behaviour)
autonomy:
  default_mode: gated            # gated | autonomous | tiered
  require_actor: true            # unattributed transitions become UNATTRIBUTED_CHANGE
  modes:
    autonomous:                  # max throughput; trust the ledger, audit after the fact
      agent_may_advance: [declared, wired, demonstrated, correctly-meant]
      human_gate: []
    gated:                       # default; flow & demonstration free, meaning gated
      agent_may_advance: [declared, wired, demonstrated]
      human_gate: [correctly-meant, brd_approval]
    tiered:                      # trust proportional to demonstrated proof
      agent_may_advance: [declared, wired]
      auto_merge_at: demonstrated      # a demonstrated unit auto-merges
      human_gate: [correctly-meant]
```

- **Per-task override.** A task may request a stricter or looser mode
  (`lattice task update <id> --mode autonomous`); the *stricter* of task and
  workspace wins for human-gated levels, so a task can never widen autonomy
  past the workspace ceiling — only narrow it.
- **The floor no mode can lower.** Independent of mode, the validator continues
  to enforce Lattice's existing safety contract, because these are correctness
  rules, not policy:
  - `llm_from_code` BRDs stay `draft` and require human approval
    (`BRD_UNAPPROVED_LLM`) — **no mode, including `autonomous`, self-approves a
    BRD.**
  - `regulatory` / `legal` / `financial` constraints are human-authored only
    and are never machine-judged or machine-written — δ's entailment check skips
    them entirely.
  These are the inviolant floor; `autonomous` mode buys speed *above* it, never
  through it.
- **Mode is recorded.** Every ledger entry stamps the `mode` under which the
  transition was made, so an audit can ask *"which claims were advanced
  autonomously vs. human-gated?"* and re-review exactly the autonomous set.

This is the answer to "fully autonomous *or* human-reviewed based on the
execution choice": it is a dial, defaulted safe, floored by correctness, and
fully recorded.

## 8. Schema & surface changes (all additive)

The v0.7 backward-compat bar holds — existing manifests validate unchanged:

```yaml
# brds/<id>.yaml
user_scenarios:
  - id: US-1
    actor: Solo user
    narrative: |
      ...
    verified_by: [test.journey.us1, ep.cli.todo]   # NEW (α), optional
```

No change to `feature`, `entry-point`, or `decision` schemas. New on-disk,
git-tracked, regenerable directories: `lattice/.cache/results/` (γ),
`lattice/.leases/` (§5), `lattice/.ledger/` (§6). New config blocks:
`autonomy:` (§7); the `agentic.llm` toggle that already exists
(`enabled: false` by default) gates δ's assisted check and nothing else.

New CLI: `lattice next`, `lattice results ingest`, `lattice lease
acquire|release|list`, `lattice ledger [rebuild]`, `--actor` / `LATTICE_ACTOR`.

## 9. New validation rules

| Code | Severity | Catches | Stream |
|---|---|---|---|
| `BRD_SCENARIO_UNVERIFIED` | warning | scenario with no verifier | α |
| `BRD_SCENARIO_UNMAPPED` | info | scenario that claims no verifier | α |
| `FEATURE_UNREACHED` | info | production feature on no entry-point flow | β |
| `SCENARIO_NO_ENTRYPOINT` | info | scenario verified only at pure-logic altitude | β |
| `VERIFIER_FAILING` | warning | ingested result for a `@verifies` test is red | γ |
| `CRITERION_INVARIANT_NARROWER` | info | invariant does not entail its criterion (assisted; no-op without LLM) | δ |
| `INVARIANT_UNFALSIFIABLE` | info | enforcer has no reachable violating path | δ |
| `INVARIANT_MUTANT_SURVIVED` | warning | a mutant of the enforcer survived the suite | δ |
| `ENFORCER_NOT_GUARD` | info | `@enforces` symbol carries the tag but guards nothing | δ |
| `LEASE_SCOPE_OVERLAP` | info | two live leases claim overlapping paths | §5 |
| `CONCURRENT_SURFACE_CONFLICT` | warning | leased working sets diverge a shared contract surface | §5 |
| `UNATTRIBUTED_CHANGE` | warning | a transition with no `actor` under `require_actor` | §6 |

Severities stay low by default so v0.8 informs before it blocks; `--strict`
and CI templates escalate per team. Assisted δ checks degrade to deterministic
no-ops when `agentic.llm.enabled: false`.

## 10. Worked example — the proof, replayable and honest

```sh
cd examples/lattice-todo-sample

# state today: green and blind. SC-2 ⊃ INV-2 is a live meaning miss;
# US-1's passing journey test is invisible because scenarios aren't walked.
lattice validate        # clean
lattice rtm             # 100% (4/4 SC) — but 0 scenarios counted

# α+β: make the scenario a unit, make reach a number
#   add  user_scenarios[US-1].verified_by: [test.journey.us1, ep.cli.todo]
lattice rtm             # US-1 row appears: DECLARED (test exists, result not ingested)
lattice coverage        # journey coverage: 1/2  ← US-2 still unmapped, honest headline

# γ: ingest the real result; "passed" now means passed
lattice results ingest junit.xml
lattice rtm             # US-1: DEMONSTRATED ; US-2: UNVERIFIED

# δ: the bug demonstration can never catch
lattice validate        # CRITERION_INVARIANT_NARROWER on SC-2:
                        #   INV-2 "two calls distinct" ⊉ "unique within a session / targets exactly one"
#   fix = widen INV-2 (or add INV-3) until the union entails SC-2 — a human gate under `gated` mode

# §4–§7: drive it as a fleet
lattice next --actor agent:A        # → "widen INV-2 to entail SC-2 (correctly-meant gap, weakest link)"
lattice lease acquire todo.add --actor agent:A
# agent A edits the slice; on commit, the ledger records the transition under its mode:
lattice ledger --unit brd.task_tracking:SC-2
#   c4f2e07  agent:A  SC-2 flagged→correctly-meant  evidence:INV-3@c4f2e07  mode:gated  (human-approved)
```

Ship `lattice-todo-sample` as a bundled example (peer to
`examples/sample-project/`): it is the minimal repro of *both halves* of the
gap — a demonstration blind spot (US-1 invisible) and a meaning miss (SC-2) —
and the regression fixture for α/β/γ/δ plus the steering layer.

## 11. Adoption guide — adopt the loop, not the ceremony

The failure mode this proposal exists to prevent is also the failure mode of
*adopting* it, and an agent fleet hits it faster than a human team. Organize
adoption around the four **questions**, with a human-trusted answer as each
exit criterion — never an artifact count.

| Phase | Question you can now answer | Done when | Anti-pattern |
|---|---|---|---|
| **0. Orient** | "What is here?" | `lattice extract` clean; `lattice coverage` read; `lattice next` returns a sane weakest-link list | Writing manifests before reading the graph |
| **1. Reach** (β) | "How does the world get in?" | Every `production` feature on ≥1 entry-point flow; no `FEATURE_UNREACHED` | Declaring features with no trigger that reaches them |
| **2. Mean** (δ) | "Does what's wired mean what we asked?" | No open `CRITERION_INVARIANT_NARROWER`; enforcers are guards, not tags | Mapping a SC to the nearest convenient invariant — or **narrowing the BRD to fit the code** |
| **3. Demonstrate** (α/γ) | "Did it actually work for the user?" | Every `user_scenario` is `DEMONSTRATED`; results ingested in CI | A passing unit test standing in for a scenario |
| **4. Gate** | "Will it stay true under a fleet?" | `lattice validate` (+`--strict`) is a required CI check; `autonomy` mode chosen; ledger reviewed per merge | Green at merge, drift by the next agent |

Three rules of adoption:

- **Lead with the scenario, not the slice.** Start each unit of work from a
  `user_scenario` and walk *down* to code, so the
  demonstrated-through-an-entry-point path is built first. This inverts the
  sample's mistake (invariants authored at unit-test altitude; scenario never
  walked).
- **Adopt depth-first on one BRD.** One BRD taken fully to *demonstrated +
  correctly-meant* teaches the loop and produces a reference chain; fifty
  features at *declared* produce a dashboard nobody trusts. `coverage` climbs on
  the *weakest* link — chase depth.
- **Turn autonomy up by truth-level, not by faith.** Start in `gated`, watch
  the ledger, and only widen a workspace to `autonomous` for the classes of
  transition the ledger shows agents getting right unattended.

## 12. Agent skills & AMA practices — use the loop, don't be bound by it

Lattice ships skills so agents wield it expertly; today they cover the *flow*.
v0.8 adds two that cover the *goal*, because an agent optimizing for `validate:
clean` reproduces the §1 gaming trap across every slice at once.

- **`achieving-goals-with-lattice`** (new). Lattice is a means to make the BRD
  goal *true*, not to satisfy its flow. Names the ceremony traps — writing a
  manifest to silence a rule, spraying `@enforces` to inflate counts, a
  `@verifies` test that asserts something easier than the invariant, **and
  narrowing the BRD until the bug is out of scope** — and prescribes goal-first
  work: orient on the graph (`lattice next`), pick the smallest change that
  moves a real RTM/journey number toward `demonstrated`, demonstrate before
  declaring, claim a lease before editing.
- **`verifying-meaning`** (new). The operational δ skill: read SC and invariant
  side by side and check entailment; **strengthen rather than remap or
  re-scope** on a narrowing; spot vacuous invariants and tag-not-guard
  enforcers; demonstrate scenarios through an entry point and ingest the result.
  Encodes the human-judgement carve-out for regulatory criteria.

**AMA as enablement, not a cage.** The AMA pillars (vertical slices, no
cross-feature imports, line caps, command-vs-query) are reframed from
constraints into the thing that *lets one agent act on one slice with one slice
of context* — and, per §5, into the concurrency primitive that lets the fleet
act in parallel. When a rule fights the goal, the move is to **reshape the
slice** (split, extend, move the seam), not to `@suppress`. The ≤500-word
`.ai-spec.md` is the loading contract: if a change needs more than the slice
and its spec, the slice is too big — propose a split before coding.

**Reach the agent at the right moment.** `views/agentcontext.go`'s
`relevant_skills` becomes goal-aware (§4): scenario/criterion work surfaces the
two goal skills first, and `lattice_get_agent_context` carries the loading hint
so the agent need not know the catalogue.

## 13. Out of scope

- **Synthesizing scenario tests and invariants.** v0.8 *verifies* a scenario
  has a passing verifier and *flags* a narrowed invariant; it does not write the
  test or widen the invariant. (`agent draft-scenario-test` /
  `agent widen-invariant` are a natural v0.9 follow-on.)
- **Auto-approving meaning.** δ's entailment check is advisory and never flips a
  status; a human (or explicit `--accept-meaning`) closes a
  `CRITERION_INVARIANT_NARROWER`. Regulatory/legal/financial criteria are never
  machine-judged. No autonomy mode overrides this.
- **A lock server or live agent bus.** Coordination is file-and-git-backed
  (§5); real-time multi-agent messaging and a hosted lease daemon are out of
  scope — the graph and its commits *are* the coordination channel.
- **Cross-commit demonstration history.** v0.8 ingests results for
  `generated_from_commit`; trend lines are a v0.9 reporting concern. The ledger
  records transitions but does not yet chart them.

## 14. Backward compatibility

Opt-in and additive end to end. A v0.7 workspace with no `verified_by` fields,
no ingested results, no `autonomy` block, and `agentic.llm.enabled: false` sees
only new `info`-level rows; its `validate` exit code is unchanged, the δ
assisted check is a deterministic no-op, and absence of an `autonomy` block
means "human approves everything" — exactly today's behaviour. Leases, ledger,
and results caches are git-tracked regenerable directories; deleting them loses
no source of truth. Teams adopt α/β/γ/δ by adding links and wiring `lattice
results ingest` into CI, then adopt the steering layer by setting `--actor`,
choosing an `autonomy` mode, and reading the ledger — nothing breaks on
upgrade.

---

_The one-line version: v0.6 let Lattice say "this is wired." v0.8 lets it say
"this is correctly meant **and** was demonstrated," refuses to conflate the
two — and then turns that honest graph into the substrate a fleet of agents
steers by: ranked next-actions off the weakest link, leases so they don't
collide, autonomy modes the operator dials, and an append-only ledger that
makes every autonomous move attributable and replayable._
